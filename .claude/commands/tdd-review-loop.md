You are the **implementer agent** and you own this entire run. The requirement to implement is:

$ARGUMENTS

Run the phases below in order. Do not skip phases. Narrate which phase and review round you're in as you go.

**This skill is autonomous by default.** It is built to run headless — driven by the documentation it's given (an acceptance-criteria checklist, a plan doc, the issue's `## What to build`, and the repo's conventions) — and to reach a human only for genuine blockers. The two modes:

- **Autonomous (default).** Every step below that says "stop and ask me", "get my confirmation", "ask me", or "escalate to me" is translated by this single global rule: **decide from the documentation and announce-and-proceed; and where a decision is genuinely undecidable-from-docs or unsafe, do NOT invent a default — emit a structured `BLOCKED:{reason, one-line detail}` line and stop.** "Announce-and-proceed" means state your decision in one line and continue (the model is the Phase-2 "Announce-and-proceed" line below); the caller overrides if it disagrees. The phases below mark, per gate, which translation applies — doc-driven announce vs. `BLOCKED`. **How a `BLOCKED` is surfaced is set by context, not by you:** if a human is present in this thread, present it and wait; if you were spawned as a subagent (e.g. by `/tdd-review-issues`), your `BLOCKED:{…}` line **is** your return value — stop and return it, the caller relays it. Either way you never silently push past a genuine blocker, and you never sit waiting on a prompt no one will answer.
- **Interactive (`--interactive`).** Restores the original gate-by-gate behavior: every "stop and ask me" prompts the human and waits. Use this when a human deliberately wants to drive the run by hand. (Parse this flag exactly like `--panel`/`--no-panel` — see Parse `$ARGUMENTS`.)

The **genuine-blocker set** (these `BLOCKED`/stop in *both* modes — never auto-defaulted): a stuck Phase 1, a contested `blocker`, the 3-round cap with findings still open, a red final green gate, an acceptance-criteria set that is missing/incoherent or contradicts the plan, a genuinely undetermined or sensitive interface, a dirty starting tree, an unresolvable requirement input (a missing/unreadable/empty requirement path, or an empty requirement after flag-stripping), and inconsistent on-disk run state on resume. Everything else is doc-driven in autonomous mode.

## Pre-flight (do this first, before parsing `$ARGUMENTS`)

1. **Confirm a git repo with commits.** Run `git rev-parse --is-inside-work-tree` and `git rev-parse --verify HEAD`. Treat anything other than the literal `true` from the first (e.g. `false` in a bare repo, which still **exits 0**) as failure, and use `--verify HEAD` (which fails on a commit-less or bare repo) rather than bare `git rev-parse HEAD` (which prints the literal string `HEAD` on a missing ref — exit 0 in a bare repo, but exit 128 in a commit-less work tree — so its status is not a dependable presence check). If either check fails (not a work tree, or zero commits), stop and tell me — every later `git diff $BASE` depends on this, and a bare/non-work-tree repo would otherwise collapse the `$TMP` prefix below to a shared constant.
2. **Choose the temp prefix `$TMP` and clear any prior run's state.** Run this first; the "why" notes follow.
```bash
TOP=$(git rev-parse --show-toplevel) && [ -n "$TOP" ] || { echo "no work tree — aborting" >&2; exit 1; }
TMP=/tmp/tdd-review-loop-$(printf %s "$TOP" | shasum | cut -c1-12)   # bare assignment — no leading $
{ rm -f "$TMP"-* ; } 2>/dev/null || true                            # clear every $TMP-<name> file from a prior crashed run
: > "$TMP-journal.md"                                                # journal is append-only — (re)create it empty
```
   The prefix is **deterministic and rediscoverable** (not random), so a mid-run context summarization can't orphan the state files hanging off it — **if you ever lose `$TMP` mid-run, recompute it exactly this way before reaching for any state file.** It is stable per checkout and distinct across separate worktrees/checkouts, so concurrent runs in *different* trees never clobber each other (runs in the *same* tree already collide on shared test artifacts per the panel shared-tree caveat, so one prefix per tree is the right boundary).

   **Treat every `$TMP-<name>` file as freshly owned by this run.** The `rm -f "$TMP"-*` clears them all up front so "absent" reliably means "not produced this run" — which matters because several are written only conditionally: `$TMP-panel-flag`/`$TMP-panel-flag-expected`/`$TMP-plan-path` (only when a flag/path was given), `$TMP-requirement-pending`/`$TMP-panel-conflict-pending`/`$TMP-path-confirm-pending` (only while a parse gate is pending), `$TMP-conflict-middle.txt` (only on the flag-conflict path), `$TMP-branch` (only once this run creates a branch), `$TMP-reviewer-id` (only once a reviewer is spawned). A path that never writes one must not read a stale copy from a prior run. The full set this run may write: `$TMP-base.sha`, `$TMP-ac.md`, `$TMP-requirement.md`, `$TMP-requirement-pending`, `$TMP-conflict-middle.txt`, `$TMP-path-confirm-pending`, `$TMP-branch`, `$TMP-exclude.txt`, `$TMP-panel-flag`, `$TMP-panel-flag-expected`, `$TMP-panel-conflict-pending`, `$TMP-plan-path`, `$TMP-mode-flag`, `$TMP-pre-snapshot.sha`, `$TMP-impl-summary.md`, `$TMP-reviewer-id`, `$TMP-merged-r1.md`, `$TMP-test-guide.md`, and the append-only `$TMP-journal.md`.

   **Why these exact forms:**
   - **Guard `$TOP` before hashing.** A bare `$(git rev-parse --show-toplevel | shasum)` pipes git's output into `shasum` regardless of git's exit status, so outside a work tree the empty string hashes to the *constant* `da39a3ee5e6b` — a shared prefix whose `rm -f` would then clobber a concurrent run's state. The `[ -n "$TOP" ]` guard aborts instead.
   - **Bare assignment, no leading `$`.** You *reference* it later as `$TMP`, but `$TMP=…` would expand the unset var and try to run `=/tmp/…` as a command.
   - **`{ … ; } 2>/dev/null || true` around the glob `rm`.** Under zsh, on a clean/first run `"$TMP"-*` matches nothing and zsh aborts the command at glob-expansion with `no matches found` and a non-zero status **before `rm` runs** — so the trailing `|| true` is the load-bearing part that lets the run continue. Neither `-f` nor `2>/dev/null` alone helps (the glob never reaches `rm`; zsh prints the message before the redirection takes effect — the brace-wrap is what routes it to `/dev/null`). A no-match here is normal, not a failure to stop on. (Equivalently, `rm -f` the named `$TMP-*` files individually, which never errors under `-f`.)
## Parse `$ARGUMENTS`

`$ARGUMENTS` is either an inline requirement/plan, or a path to a plan doc (e.g. `docs/some-plan.md`), optionally wrapped in a round-1 mode flag (`--panel`/`--no-panel`) and/or an execution-mode flag (`--afk`/`--autonomous`/`--interactive`).

**Execution-mode flag (`--afk` / `--autonomous` / `--interactive`).** Autonomous is the default. `--afk` and `--autonomous` are synonyms that **explicitly affirm** the default (useful so a caller is self-documenting and unaffected if the default ever changes); `--interactive` **overrides** to gate-by-gate prompting. Detect any of these with the *exact same* discipline as `--panel`/`--no-panel` below: a token counts only when the **whole first or last whitespace-delimited token** equals it (ASCII-literal, case-sensitive); a mid-text occurrence is requirement prose. When `--interactive` is present, set interactive mode and **persist the literal token to `$TMP-mode-flag`** (re-read it wherever a gate decides announce-vs-prompt; the file's **absence means autonomous**, the default — `--afk`/`--autonomous` therefore write nothing, they just confirm the default). **Strip every honored mode token** (and any round-1 flag) from `$ARGUMENTS` before the empty-check. The mode flag is independent of `--panel`/`--no-panel` and may co-occur (e.g. `--afk --no-panel <req>`); strip each honored token. (Passing both `--afk`/`--autonomous` *and* `--interactive` is contradictory — if both appear, `--interactive` wins and you announce that you did so; this needs no separate conflict gate.)

Parse the rest in this exact order — the flag-and-conflict check runs **before** the empty-check. **Every "stop and ask me" gate in this parse section is a genuine blocker, not a doc-driven decision:** in autonomous mode you cannot invent a requirement from nothing, so emit `BLOCKED:{empty_requirement}` (the step-4 empty-check) or `BLOCKED:{bad_requirement_path}` (the step-2 flag conflict that leaves no requirement, and the step-5 missing/unreadable/empty or unconfirmed-non-doc path) instead of prompting; the `--interactive` prompts spelled out in each step apply only in interactive mode.

1. **Detect the round-1 mode flag.** Look only at the **first and last whitespace-delimited tokens** of `$ARGUMENTS`. A token is a flag only if the *whole token* equals `--panel` or `--no-panel` — matched **case-sensitively as an ASCII literal** (two ASCII hyphens). `--PANEL`, a unicode-dash `—panel`, or a token like `--panel-feature.md` that merely *starts with* the string does **not** match (leave `$PANEL_FLAG` unset and fall through to the Phase-2 heuristic). Never infer the mode from the bare word "panel" inside the requirement text ("implement the admin **panel**" is a requirement, not a flag). A flag is honored **only at the first/last token**; an *opposite* flag buried mid-text (e.g. `--panel do X --no-panel ASAP`, where the last token isn't a flag) is intentionally treated as requirement prose, not a conflict — the Phase-2 announce-and-proceed mode line plus my override is the safety net.
2. **Conflict check (first, before the empty-check).** Only when `$ARGUMENTS` has **at least two tokens** AND both the leading and trailing token are flags (a lone `--panel` is one token — it skips this check and goes straight to step 3):
   - **They disagree** (`--panel … --no-panel`): **before stopping, extract and persist the middle text** (everything between the two flag tokens) to **`$TMP-conflict-middle.txt`** (NOT `$TMP-requirement.md` — that file must stay absent until step 5 resolves a real requirement, or the step-4 empty-check resume guard at the empty-check below would see a stale empty breadcrumb and fail to fire), so a context summarization during the wait can recover it. (This middle text is the *raw* argument — it may itself be a plan-doc **path** rather than requirement prose; that's fine, it's only a recovery breadcrumb for the wait window. Once I answer, re-read that breadcrumb and re-run step 4 on it — which runs the empty-check, then path-vs-inline, resolving a path to the doc's contents and persisting `$TMP-requirement.md` for the first time this run.) Then stop and ask me which mode I want — **even if no requirement text remains** after stripping them — and record **no** `$PANEL_FLAG` until I answer. When I answer, **persist it to `$TMP-panel-flag`** (step 3) and **treat the two conflicting flag tokens as consumed — drop the leading and trailing flag *tokens* specifically (don't regex-replace, which can leave one behind) before re-evaluating from step 4** (not step 5 — re-entering at step 5 would skip the empty-check and feed an empty requirement into Phase 0 when no middle text remains), so re-parsing cannot re-detect the same conflict and loop. Don't let the empty-check pre-empt this. **Also write a `$TMP-panel-conflict-pending` sentinel when you stop, and delete it the moment you persist my answer to `$TMP-panel-flag`; on a resume, if that sentinel exists and `$TMP-panel-flag` is still absent, re-ask the mode question rather than falling through to the Phase-2 heuristic.**
   - **They are identical** (`--panel … --panel`): they agree — record `$PANEL_FLAG` and persist it per step 3, **then** strip **both** tokens.
3. **Record and persist the flag.** If a (non-conflicting) flag is present — or once I resolve the conflict re-prompt in step 2 — record it as `$PANEL_FLAG` and **write the literal flag token (`--panel` or `--no-panel`, verbatim — do not normalize to `panel`/`true`) to `$TMP-panel-flag` immediately** (Phase 2 matches that exact string), **and write a `$TMP-panel-flag-expected` sentinel alongside it** — before any re-prompt below, and before the rest of git-hygiene — so a context summarization across the re-prompt or Phases 0–1 can't silently drop the mode I chose (you'll re-read it from there in Phase 2; the sentinel lets Phase 2 tell "no flag was ever set" apart from "a flag was set but its file was lost" — see Phase 2 step 1). Then strip **only the leading and/or trailing flag token(s) you honored in step 1** from `$ARGUMENTS` — never a mid-text `--panel`/`--no-panel`, which is requirement prose to keep verbatim (e.g. `--panel do X --no-panel ASAP` → `do X --no-panel ASAP`). If neither token is a flag, `$PANEL_FLAG` is unset, no `$TMP-panel-flag-expected` sentinel is written, and the mode is chosen by heuristic in Phase 2.
4. **Empty check.** If the remaining text is empty — originally empty, or empty after a flag strip (e.g. I passed only `--panel`) — ask me for the requirement before doing anything else — **and write a `$TMP-requirement-pending` sentinel when you stop, deleting it only once a non-empty `$TMP-requirement.md` is persisted in step 5; on resume, if that sentinel exists, re-ask rather than advancing to Phase 0 — key this on the sentinel alone, regardless of `$TMP-requirement.md` (the `$ARGUMENTS` you stripped may be gone after a context drop, and the conflict breadcrumb deliberately lives in `$TMP-conflict-middle.txt` so `$TMP-requirement.md` stays absent until a real requirement is resolved).** `$PANEL_FLAG` **persists across that re-prompt** (it's already on disk) and applies to the requirement I then supply — don't discard the mode I explicitly chose. **Treat the text I supply as the new remaining text and run step 5 on it** (classify path-vs-inline and persist `$TMP-requirement.md`, plus `$TMP-plan-path` if it's a doc/confirmed-file path) rather than skipping straight to Phase 0.
5. **Path vs. inline (decide on the *remaining* text).** It **"looks like a file path"** only if it is a single whitespace-free token that either contains a `/` separator or ends in a `.<ext>` suffix **whose extension is alphabetic** (e.g. `.ts`, `.md`, `.yaml`). Anything else — multi-word text (even if it contains a slash, like "fix a/b testing bucket assignment"), a bare single word with no extension (like "checkout"), or a token whose only dotted suffix is **numeric/version-like** (`v1.2`, `3.0`, `node18.4`) — is an **inline requirement**, not a path. (Precedence: a single token **containing `/`** is path-like regardless of its suffix — so `release/v1.2` is a path; the numeric/version-suffix exclusion applies only to **slash-free** tokens like `v1.2`.)
   - **Resolve the token against the repo toplevel first:** `PLAN=$TOP/<token>` (reusing `$TOP` from Pre-flight; if the token is already absolute, use it as-is to avoid a `$TOP//abs` double slash). Run every readability/emptiness check and every read in this step against `$PLAN`, not the bare token — the harness may reset your cwd between calls, so a repo-root-relative token read from the wrong cwd would spuriously fail and wrongly trip the gate below.
   - **Path-like but missing, unreadable, or empty (whether doc or non-doc — check this FIRST, before the doc/non-doc split below):** stop and ask me, rather than silently treating the path string itself as the requirement. **Write a `$TMP-path-confirm-pending` sentinel recording the token when you stop; on resume, if it exists and `$TMP-requirement.md` is absent, re-ask rather than silently treating the path string as the requirement — delete it once step 5 persists the requirement.** When you stop, name whether it *looked* like a plan doc or a source/config file so I can correct the path. **When I supply a corrected path, re-evaluate from step 4 on the new text** (run the empty-check first, then path-vs-inline — not step 5, which would skip the empty-check and feed an empty/whitespace corrected path straight into Phase 0) **— don't re-run Pre-flight (its up-front `rm` already ran this run).**
   - **Doc extension** (`.md`/`.txt`/`.rst`/`.markdown`), readable and non-empty: read `$PLAN` and treat its contents as the requirement. **Persist `$PLAN` (the absolute path resolved above) to `$TMP-plan-path`** — not repo-root-relative, because `$TMP-plan-path` is re-read by spawned subagents (Phase 3) and the recovery step whose cwd is not guaranteed to be the repo toplevel, so an absolute path is the only form that resolves regardless of cwd. Phase 3 needs it and it must survive summarization.
   - **Path-like, readable and non-empty, but NOT a doc extension** (a slash-bearing token, or any other extension — e.g. `src/auth/session.ts`, `infra/deploy.yaml`, `scripts/run.sh`, `config.json`): this could be source/config, not a plan. Don't *silently* distill acceptance criteria from it — **confirm with me** that I meant that file as the plan before proceeding (**write a `$TMP-path-confirm-pending` sentinel recording the token when you stop, and on resume with the sentinel present and `$TMP-requirement.md` absent, re-ask rather than falling through — delete it once step 5 persists the requirement; same crash-recovery discipline as the missing-path gate above**). **If I confirm it is the plan, read `$PLAN` and treat its contents as the requirement (proceed exactly like the doc-extension branch above) — and persist `$PLAN` (absolute) to `$TMP-plan-path`. If I say it is not the plan, ask me for the actual requirement, then treat my reply as the new remaining text and re-evaluate from step 4 — and do NOT persist `$TMP-plan-path` (a path I just rejected is not a plan doc; leaving the file absent keeps the Pre-flight "absent = not produced this run" invariant, so Phase 3 and the recovery step correctly treat this run as plan-doc-less).**

   **Whichever branch resolves the requirement (inline text, a doc's contents, or a confirmed source/config file's contents), once you have the final requirement text, persist it to `$TMP-requirement.md`** — `$ARGUMENTS` is a one-time template expansion that is never written to disk and may not survive a context summarization, so the Phase-2 crash-recovery step re-reads the requirement from here rather than relying on `$ARGUMENTS`.

## Pre-run git hygiene (do this before capturing the base commit)

1. **Check for a dirty starting tree:** run `git status --porcelain`. If it's non-empty, the working tree already has changes that would otherwise be wrongly attributed to this requirement (folded into the diff the reviewer, the `$AC` pass, the bite audit, and the Phase-3 guide all consume). **In autonomous mode**, do not stash/commit/guess: emit `BLOCKED:{dirty_tree, <paths>}` and stop — the caller (e.g. `/tdd-review-issues`) resolves pre-existing paths up front and/or hands you an exclusion list, so on a clean handoff this never fires; if the caller *did* hand you an exclusion list (`$TMP-exclude.txt` already populated) that fully covers the dirty paths, treat the tree as clean and proceed. **In `--interactive` mode**, **stop and ask me** how to proceed — stash, commit, or explicitly record the pre-existing paths so you can exclude them from "the diff" throughout. Do not silently absorb them. **If I choose to record paths**, extract a clean exclusion set into `$TMP-exclude.txt`, one **raw, un-quoted** path per line, using a NUL-safe pipeline so paths with spaces survive: run **`git status --porcelain -z`** and split on NUL. **Strip the 3-char status field only from the leading, status-bearing field of each entry** to get the raw path. **Do not use plain `cut -c4-` on the non-`-z` output** — that output **C-quotes** any path containing a space (e.g. `"a b.ts"`), and the literal quotes then defeat the pathspec match while `cut` also can't see the NUL framing. **Renames/copies need both sides, and only the first field is status-bearing:** in `-z` mode a rename/copy is emitted as **two** NUL-separated fields with **no `->` arrow**, in **reverse** of the display order — the **new (destination)** path comes first (prefixed with the `R…`/`C…` status, so strip its 3 chars), then the **old** path as a **bare field with NO status prefix — record it verbatim, do NOT strip 3 chars off it** (stripping `old/a.ts` → `/a.ts`, which git rejects as outside the repo with a fatal exit-128 that kills every scoped diff). Record **both** the new and the old path (git models a rename as delete-old + add-new, so excluding only the new path still leaks `D <old>` into the scoped diff). A raw porcelain line like ` M src/x.ts` fed straight to a pathspec, or a C-quoted `"a b.ts"`, will silently fail to exclude anything. A concrete builder (run under **bash**, whose `read -d ''` does the NUL-splitting; the consumption recipe below is shell-agnostic):
```bash
: > "$TMP-exclude.txt"
while IFS= read -r -d '' entry; do
  printf '%s\n' "${entry:3}" >> "$TMP-exclude.txt"            # status-bearing field -> strip the 3-char status
  case "${entry:0:1}" in
    R|C) IFS= read -r -d '' old && printf '%s\n' "$old" >> "$TMP-exclude.txt" ;;  # paired old path: bare field, do NOT strip
  esac
done < <(git status --porcelain -z)
```
That file becomes the canonical exclusion set used everywhere "the diff" is computed.
2. **Branch off the default/protected branch:** run `git branch --show-current`. If it's the default branch (`main`/`master`) or otherwise protected, `/tdd`'s red-green-refactor commits and bite-audit reverts would land directly on it. **In autonomous mode**: if on `main`/`master`, branch automatically to `tdd-review-loop/<short-slug-of-requirement>` (the default name), announce it, and proceed — do not ask whether or what to name it; if on a non-personal branch you cannot classify as a feature branch you or your caller created for this work (e.g. a `tdd-review-loop/*` or `tdd-review-issues/*` branch, **or any branch your caller's spawn prompt explicitly says it created for this stacked work** — trust that statement as authoritative classification even when the branch name matches no known prefix), emit `BLOCKED:{protected_branch}` rather than guessing. (When the caller already put you on its own feature branch — as `/tdd-review-issues` does — this is a no-op: implement in place, no new branch is cut. Note `/tdd-review-issues` stacks on whatever branch the human was already on, so that branch may be named **anything** — not necessarily a `tdd-review-issues/*` name; when its prompt tells you that you are on the caller-created feature branch for this work and must not branch, honor that in place rather than emitting `BLOCKED:{protected_branch}` over the unfamiliar name.) **In `--interactive` mode**: **Branch protection lives on the remote and may not be queryable from here (no guaranteed `gh`/API access), so do NOT assume a non-`main`/`master` branch is unprotected** — if the current branch is anything other than an obviously-personal/feature branch you created this run, stop and ask me whether to branch off before Phase 1. **On `main`/`master` specifically, branching is effectively mandatory** — ask only for the name (default `tdd-review-loop/<short-slug-of-requirement>`), not *whether* to branch; if I explicitly insist on staying on `main`/`master`, require an explicit acknowledgement from me that commits will land there before proceeding, rather than silently committing onto it. When you do branch, name it `tdd-review-loop/<short-slug-of-requirement>` unless I specify otherwise, so the run's commits are isolated, **and persist the chosen name to `$TMP-branch`** (so the post-escalation resume can re-identify this run's branch; `git branch --show-current` is the fallback). **If that branch already exists** (a prior or crashed run of the same requirement), don't let `git checkout -b` fail with exit 128 — **verify-before-create with a bounded loop:** `slug=tdd-review-loop/<base>; n=1; while git show-ref --verify --quiet "refs/heads/$slug"; do slug=tdd-review-loop/<base>-$n; n=$((n+1)); [ $n -gt 5 ] && break; done` then `git checkout -b "$slug"`; if it's still taken after the cap, stop and ask me for an alternate name.

**Then record the base commit so diffs work for the whole run regardless of what gets committed later:**
```
git rev-parse HEAD
```
Call this `$BASE`. **Persist it immediately** to `$TMP-base.sha` — `$BASE` is just a value in your context, and once `/tdd` starts committing you can no longer re-derive it from `git rev-parse HEAD`; re-read it from the file whenever you need it after commits land.

Throughout this run, "the diff" always means `git diff $BASE` plus `git status --porcelain` for any untracked files (and `git diff $BASE -- <new files>` once added), **minus any pre-existing paths recorded in step 1**. Never rely on a bare `git diff`, which shows only unstaged changes and will miss work that TDD has already committed or staged.

**Propagating the exclusion set:** if step 1 recorded pre-existing paths to `$TMP-exclude.txt`, that file is the canonical exclusion set. Anywhere this run computes "the diff" — including the Phase-2 mode heuristic, every reviewer/panelist, and the Phase-3 guide agent — scope it explicitly with **this single canonical recipe, which is space-safe by construction:**
```
args=(. )
[ -f "$TMP-exclude.txt" ] && while IFS= read -r p; do [ -n "$p" ] && args+=( ":(exclude)$p" ); done < "$TMP-exclude.txt"
git diff $BASE -- "${args[@]}"                             # tracked + already-committed changes
git ls-files --others --exclude-standard -- "${args[@]}"  # untracked files git diff $BASE can't see — inspect each's contents too
```
**Never use a `$(sed …)`/`$(cat …)` command-substitution form** like `git diff $BASE -- . $(sed 's/^/:(exclude)/' $TMP-exclude.txt)` — it word-splits any multi-word path into separate *positive* pathspecs that silently invert the exclusion (restricting the diff instead of excluding), and embedded quotes are treated as literal path characters; both fail with **exit 0 and no error**. Paste both `$BASE` (from `$TMP-base.sha`) and the contents of `$TMP-exclude.txt` into each subagent's prompt and instruct them to build the pathspec the same way — **including the `git ls-files --others --exclude-standard` half**, since the bare `git diff $BASE -- … :(exclude)…` form they're often handed is blind to untracked files — so they see the same scoped diff you do. If no paths were recorded, `$TMP-exclude.txt` is absent, the `[ -f ]` guard leaves the exclusion set empty, and a bare `git diff $BASE` is already correct. **Tell each subagent to run these git commands from the repo toplevel (`$TOP` from Pre-flight)**, since `.` and `git diff $BASE -- .` are cwd-relative and a subagent whose cwd isn't the repo root would otherwise scope the diff to a subdirectory.

## Phase 0 — Acceptance criteria

Before writing any code, distill the requirement into an explicit, **numbered acceptance-criteria checklist** — each item a single observable behavior or constraint the finished work must satisfy, phrased so it can be objectively checked as met/unmet (not "handles errors well" but "returns a 422 with field-level messages when the payload is missing `email`"). Include negative/edge criteria where the requirement implies them. For a purely presentational criterion that can only be confirmed by eye (spacing, font, layout), mark it as such — it will be verified by human visual check, not asserted "met" by a headless agent.

**Autonomous mode (default):** if the requirement already carries an acceptance-criteria checklist (e.g. the issue's `## Acceptance criteria` section — `/to-issues` output is already human-approved), **adopt it verbatim** as `$AC`, persist it, announce it in one line, and proceed straight to Phase 1 — do **not** re-distill and do **not** confirm. If no such checklist is present, distill one as above, announce it, and proceed without waiting. Emit `BLOCKED:{ac_missing}` only if you cannot form a coherent checklist at all, or `BLOCKED:{ac_contradicts}` if the supplied criteria materially contradict the requirement/plan (e.g. the `## Acceptance criteria` and `## What to build` disagree). **Interactive mode (`--interactive`):** Show me the checklist and **get my confirmation before implementing.** If I give edits, apply them and **restate the final checklist, then loop** — confirm again — until I approve it with no further edits (don't proceed on your own interpretation of an edit). If the requirement is a one-line bug fix, this can be a single criterion — but still write it down (you may fold this single-criterion confirmation into the same message as your implementation plan — **but you must still wait for my approval before starting Phase 1; folding only saves a round-trip, it does not waive the gate**). This checklist (call it `$AC`) is the contract for the whole run: it scopes Phase 1, it's what the reviewer ticks off in Phase 2, and convergence is illegal while any criterion is unmet (see Phase 2).

**Persist `$AC` so it survives verbatim across subagent handoffs:** once I approve it, write the final checklist to `$TMP-ac.md` (the same disposable-file pattern this command uses for `$BASE`, the exclusion list, and the Phase-3 guide). Treat that file as the source of truth and **re-read it** at each handoff (every reviewer spawn, every `SendMessage`, the Phase-3 spawn) rather than relying on it staying intact in your context — paste its exact contents into each subagent prompt.

## Phase 1 — Implement with TDD

Invoke the `/tdd` skill and implement the requirement using its red-green-refactor workflow. Follow `/tdd` fully — in `--interactive` mode that includes confirming the interface and which behaviors to test with me where that skill calls for it; in autonomous mode `/tdd` derives and announces them per the passthrough below. Every `$AC` criterion that warrants a test (per the scoping rules below) should map to at least one test.

**Pass the execution mode through to `/tdd`** (re-read `$TMP-mode-flag`): in **autonomous mode** tell `/tdd` it is running autonomously, so it derives the public interface and the behaviors-to-test from `$AC` + the plan doc + repo conventions and **announces-and-proceeds** (its own "Autonomous mode" branch) instead of waiting at its Planning checkpoints — escalating to a `BLOCKED:{interface_underdetermined}` / `BLOCKED:{sensitive_surface}` only on a genuinely undetermined or sensitive interface. In **`--interactive` mode** let `/tdd` confirm the interface and behaviors with me at its checkpoints as usual.

**Frontend test scoping:** Do *not* write tests for frontend/UI code by default. Skip tests for presentational components, layout/styling, simple prop wiring, trivial event handlers, and thin glue that just calls a hook or renders data. Only write frontend tests when the code carries **non-trivial logic worth protecting** — e.g. meaningful data transformation/derivation, conditional branching with several states, form validation rules, reducers/state machines, custom hooks with real logic, or tricky edge-case handling. In that case, prefer testing the logic in isolation (extract it to a pure function/hook and test that) rather than rendering the whole component. When in doubt about whether a given piece of frontend logic is "complex enough," ask me before writing or skipping the test — but don't interrupt per-component: collect all in-doubt frontend-scoping questions and raise them together at the `/tdd` "list of behaviors to test" checkpoint, so I draw the trivial/non-trivial line once for the whole change. **In autonomous mode** apply this line mechanically instead of asking: >1 conditional branch or any real data derivation/transformation → extract and test it; otherwise skip; announce the calls you made; reserve a `BLOCKED:{test_scope_borderline}` only for a borderline that touches money/validation/data-integrity. This scoping rule applies only to frontend code; backend/business logic follows `/tdd` as normal.

**Note:** in **`--interactive` mode** this phase is not fully autonomous — `/tdd` will pause to get my approval on the interface and the list of behaviors to test; wait for my input at those checkpoints rather than guessing. In **autonomous mode** `/tdd` runs without those pauses per the passthrough above, stopping only for a genuinely undetermined/sensitive interface (`BLOCKED`).

When implementation is complete, **gate the handoff on a fully green state**: run the entire test suite, plus typecheck and lint if the project has them. Everything must pass before moving to Phase 2 — don't make the reviewer burn a round on breakage you could catch here. **If `/tdd` can't reach green within reason** (treat ~3 consecutive failed green attempts on the same failure, or no measurable progress across attempts — the same test/error oscillating green/red with no net advance — as "stuck"), escalate (autonomous: emit `BLOCKED:{phase1_stuck}`) rather than handing off red or thrashing — the same stop-and-ask discipline the Phase 2 gates apply.

**Bite check (do this yourself before handoff):** for each of your 2–3 most important new tests (most important = the highest-risk / most load-bearing logic, tie-broken by `$AC`-criticality), deliberately break the code it covers (flip a condition, drop a guard, return the wrong value) and confirm that test *fails*, then revert. A test that stays green against broken code is not protecting anything — fix or strengthen it before handoff. (If only one test exists, bite-check that one.) Record which tests you bite-checked; you'll report this to the reviewer.

**Make every bite revert-safe** (here and everywhere else this run breaks-then-reverts code — the reviewer's bite audit too): snapshot before breaking and restore from the snapshot rather than hand-editing the break back, so a crash mid-break can't leave the tree broken. Concretely: stash or commit clean state first (e.g. `git stash` / a throwaway WIP commit, or note the exact `git checkout -- <file>` that restores it), break, observe the failure, then **restore from the snapshot** and verify `git diff $BASE` is back to where it was. If you ever find the tree broken with no record of how to restore it, stop and tell me rather than guessing.

**Zero-test branch:** if the requirement legitimately warrants no tests (e.g. a purely presentational frontend change under the scoping rule above), the test-centric gates degrade gracefully — make that explicit rather than inventing tests to satisfy them: the bite check and the reviewer's bite audit are **N/A**, "all audited tests bite" is **vacuously true**, and both green gates fall back to **typecheck + lint + manual `$AC` verification** (walk each criterion by hand, since there are no tests to assert it — and for any presentational criterion that can only be confirmed by eye, mark it "pending human visual check," not "verified met"). Say so in your handoff summary so the reviewer doesn't raise "missing tests" against an intentionally test-free change.

Then capture a summary of what you built (files changed, key decisions, the diff — computed per the "the diff" definition in the Pre-run git-hygiene section: `git diff $BASE` **plus** any untracked files, scoped by the exclusion list — the `$AC` checklist with each item mapped to where it's satisfied + tested, and your bite-check results, **including exactly which tests you bit**) — you'll hand this to the reviewer. **Persist this summary to `$TMP-impl-summary.md`** (the same disposable-file pattern as `$AC`/`$BASE`) and re-read it at each reviewer handoff: a raw diff recovers the code but not the "key decisions" or "which tests I already bit" the reviewer needs (the latter drives its "spot-check *different* tests" step), so these must survive a context drop on disk, not just in context.

## Phase 2 — Review loop (up to 3 rounds)

### Round-1 mode: single reviewer vs. reviewer panel

Round 1 is the discovery round — breadth matters most here. You may run it either as a single reviewer or as a parallel **panel** of lens-specialized reviewers whose findings you merge. Rounds 2–3 are *always* a single-reviewer dialogue regardless of round-1 mode (see below).

Decide the mode before spawning anything, in this order:
1. **If `$PANEL_FLAG` is set:** re-read it from `$TMP-panel-flag` (don't trust it surviving in context across Phases 0–1) — `--panel` → use the panel; `--no-panel` → use a single reviewer. The flag always wins. **If `$TMP-panel-flag` is absent or empty, check `$TMP-panel-flag-expected`:** if that sentinel is *also* absent, no flag was ever set this run — fall through to the heuristic in step 2. If the sentinel is **present** but `$TMP-panel-flag` is gone, a flag *was* chosen and its file was lost to a context drop — do **not** run the heuristic (it could flip an explicit `--no-panel` to panel on a security-sensitive diff, the opposite of what I chose); stop and ask me which mode, then re-persist `$TMP-panel-flag`.
2. **Otherwise, heuristic on the Phase 1 diff:** use the **panel** if **`(≥3 files)` OR `(≥150 changed lines)` OR `(sensitive-path AND (>20 changed lines OR spans >1 such file))`** — where a *sensitive* path is one you'd consider security-, money-, or data-integrity-sensitive (auth, payments, billing, permissions, migrations, deletion/PII handling). The explicit grouping matters: a 1–2 line fix on a sensitive path **alone** is **not** enough (the `AND` binds only the sensitive-path disjunct — don't spin up a 4-reviewer panel for it), but a ≥3-file or ≥150-line change qualifies regardless of sensitivity. Otherwise use a **single reviewer**. Measure size the same way "the diff" is defined (Pre-run git-hygiene): `git diff $BASE --shortstat` **scoped to exclude recorded pre-existing paths** in `$TMP-exclude.txt` (so a dirty starting tree can't inflate the count), **plus** any still-untracked files — discover them with `git ls-files --others --exclude-standard` (use this, **not** `git status --porcelain`, for the file count: porcelain collapses an entirely-new directory to a single `?? dir/` entry and would undercount; to get untracked *line* counts pipe each file through `wc -l`, or `git add -N` them and re-run `git diff $BASE --shortstat`) — `--shortstat` is **blind to untracked files**, and a common TDD outcome (a new source module + new test file, still untracked at handoff) would otherwise score ~0 lines and wrongly drop to single-reviewer mode. Note `--shortstat` **omits the clause for any zero count** (a pure-add prints only `N insertions(+)`, a pure-delete only `N deletions(-)`, an empty diff prints nothing) — read whichever clauses are present and treat a missing one as 0, not the whole measurement as 0.

**Announce-and-proceed:** state in one line which mode you're using and why (e.g. "Round-1 mode: panel — diff touches 6 files / 240 lines" or "Round-1 mode: single — 1 file, 18 lines"), then proceed. Don't stop to ask; I'll override if I disagree.

**Panel mode — round 1 only.** **First, capture the Phase-1-handoff HEAD:** record `$PRE_SNAPSHOT` = `git rev-parse HEAD` and persist it to `$TMP-pre-snapshot.sha` **before spawning any panelist** — the panel teardown below asserts `HEAD == $PRE_SNAPSHOT` to catch a rogue panelist commit, so this reference must exist (the panel makes no commit, but the assert still needs something to compare against — `$BASE` won't do, since HEAD ≠ `$BASE` after `/tdd`'s commits). Then spawn 3–4 `general-purpose` reviewers in parallel (single message, multiple tool calls). **Default to all 4 lenses** (below); drop to 3 only for a smaller-but-still-panel-worthy diff (see the fold-down note). Give each the same round-1 reviewer context (requirement, `$AC`, `$BASE` and the exclusion list, implementation summary, frontend scoping rule), with two differences: assign each a distinct **lens** and tell it to confine its findings to that lens, and tell it it is **read-only** — it may read and report, but must not edit/mutate the tree.

**Read-only evidence gate for panelists (replaces the write-and-run evidence gate):** because panelists are read-only and (mostly) don't run the suite, do **not** hold them to the Phase-2 evidence gate that demands a failing test they wrote and ran. Instead require each panel finding to cite a specific `file:line` and give precise **observed-vs-expected reasoning** (what the code does on what input vs. what it should do). Panel findings are **provisional**: the single post-merge reviewer (below) converts the surviving ones into evidence-backed findings before convergence is judged — so a real bug a panelist spots is never demoted to `nit` merely for lacking a written repro.

**Shared-tree caveat (important — the panel shares one working tree):** there is no harness-level write lock, so "read-only" is an *instruction the panelist may still violate*, and **concurrent test runs collide** on non-namespaced artifacts (`.pytest_cache`, coverage files, `__pycache__`, snapshots, `dist`/`build`/`target`, test DBs, fixed ports), producing flaky failures a panelist would then misreport as a real finding. So do **not** have all panelists run the suite: have exactly **one** panelist (or none) run it, and tell the others explicitly **not** to — they review statically and against the green suite output you already captured at the Phase 1 handoff. Their findings follow the read-only evidence gate above (`file:line` + observed-vs-expected reasoning), so not running the suite does **not** cap them at `nit`. This shared-tree (static) panel has no worktree/commit state to strand, and the read-only gate plus the serial post-merge re-verification give full-severity coverage without concurrent suite runs.

**Panel teardown — run on every exit path** (panelists returned normally, one errored/aborted, or you stopped). No worktrees or WIP commit exist, so teardown is: confirm via `git status --porcelain` and the scoped `git diff $BASE` that the tree still matches the Phase 1 handoff, and `git checkout`/`git stash -u` away any stray change a panelist made despite the read-only instruction. **Also assert HEAD == `$PRE_SNAPSHOT`** (re-read `$TMP-pre-snapshot.sha`) so a rogue panelist *commit* — which the porcelain/diff checks can't see — is surfaced rather than silently carried: if HEAD moved, emit `BLOCKED:{rogue_panelist_commit}` (autonomous) or stop and tell me (`--interactive`).

Either way, tell every panelist it must **not** emit a `STATUS:` line (convergence is judged only by the single reviewer in the dialogue rounds). The lenses:
- **correctness** — logic bugs, wrong outputs, broken control flow, mishandled return values.
- **edge-cases / concurrency** — boundaries, nulls/empties, error paths, races, ordering, partial failures.
- **requirements-coverage** — walk the `$AC` checklist; find criteria that are unmet, partially met, or untested.
- **test-quality** — by inspection only: find weak, tautological, or non-biting tests and untested logic, and **nominate** the 2–3 tests most worth a bite audit (don't run the audit — that's deferred to the serial step below). *(If Phase 1 was the intentional **zero-test** case, this lens instead confirms no tests were warranted — there's nothing to nominate, and that's expected, not a finding — but it should still flag any genuinely non-trivial logic that was left untested, per the Phase-1 frontend scoping rule.)*

(Drop to 3 lenses — folding edge-cases into correctness — only when the diff is panel-worthy purely on the high-risk disjunct, OR is just over a single size threshold: **<5 files AND <250 changed lines AND no concurrency/async/ordering/partial-failure surface**. If the diff has real concurrency/async/ordering surface, keep edge-cases/concurrency as its own dedicated lens regardless of size.)

When the panelists return — **even if one errored or aborted** — **first run Panel teardown** (above) to restore a clean tree on every exit path, and confirm the tree still matches the Phase 1 handoff state. Then **merge their findings** into one numbered list:
- Collapse entries only when they describe the **same defect / root cause** (not merely the same `file:line`), keeping the highest severity and strongest evidence.
- Demote any blocker/should-fix that failed the **read-only evidence gate** (no `file:line`, *or* no observed-vs-expected reasoning) to an unverified `nit` — but **tag it `recheck`**. A `recheck` nit is not a silently-ignored finding: the post-merge reviewer (below) must independently re-investigate every `recheck` nit before its first `STATUS:` and **re-promote** any it can reproduce, so a real bug a panelist spotted but under-documented can't slip out as a non-blocking nit.
- Carry the test-quality lens's bite-audit nominations forward separately.
- **Persist the merged list to `$TMP-merged-r1.md`** — it's the round-1 reconstruction source if the post-merge reviewer dies (see below). **Produce it even if it's empty.**

(Panelists are discarded after round 1 — don't try to resume them.)

Then spawn **one** `general-purpose` reviewer — **always spawn it, even if the merged list is empty**, since it is the only source of the round-1 `STATUS:` line. **Record this post-merge reviewer's agent id/name the moment you spawn it** — note it in your working state and **write it (overwriting) to `$TMP-reviewer-id`**, exactly as the single-reviewer paragraph below does, so the round-1 `SendMessage`-once recovery (in the "Missing or unparseable round-1 STATUS" step) has a durable handle after a context drop. **Hand it the full single-reviewer "Round 1 reviewer context" block below** (requirement, `$AC` verbatim, `$BASE` and the exclusion list, the evidence gate, the acceptance-criteria pass, frontend scoping, etc.) *plus* the merged list as the round-1 findings — it owns the `$AC` pass and the convergence judgement from here on, so it must not be left to re-derive that context. It now has the tree to itself, so it must also re-establish evidence: convert the panel's **provisional** findings into evidence-backed ones under the real evidence gate, **independently re-investigate every `recheck` nit and re-promote any it reproduces**, and run the **test-bite audit serially** on the nominated tests (plus any others it judges important): break the covered code, confirm the test fails, revert. Any test that stays green against broken behavior becomes a `blocker` ("test does not bite") added to the findings. **(If Phase 1 was the intentional zero-test case, the bite audit is N/A — see the Phase-1 zero-test branch; say so and verify `$AC` by hand instead of inventing tests.)** **Instruct it to emit the `STATUS:` line in this first response** (covering the merged list plus its bite-audit result) — otherwise panel mode has no round-1 convergence signal and a clean diff can't exit early. Never let the loop silently degrade into three context-free reviews.

**Missing or unparseable round-1 `STATUS:` line:** the stopping conditions are read from the reviewer's `STATUS:` line, so a *round-1* reviewer (the single-mode reviewer, or the panel's post-merge reviewer) that crashes, aborts, or returns no parseable `STATUS:` leaves the loop with no convergence signal. **Never treat an absent `STATUS:` as `CONVERGED`.** Recover in order:
1. **If the reviewer is still live, `SendMessage` it once** asking only for the `STATUS:` line. Re-read its handle from `$TMP-reviewer-id` if a context drop lost the in-memory one.
2. **If it died or still returns nothing parseable, re-spawn a fresh `general-purpose` reviewer** and **overwrite `$TMP-reviewer-id`** with the new agent's id the moment you spawn it (so rounds 2–3 `SendMessage` resume targets the live reviewer, not the corpse) — overwrite, do not append a second id.
3. **Reconstruct the new reviewer's context** from on-disk state: `$TMP-ac.md`; `$BASE` (re-read from `$TMP-base.sha`) + the exclusion list (`$TMP-exclude.txt`); the requirement from `$TMP-requirement.md` (for a doc/confirmed-file run, equivalently the file at `$TMP-plan-path`); the implementation summary incl. which tests were bit from `$TMP-impl-summary.md`; **panel mode only:** the merged findings from `$TMP-merged-r1.md`; plus any findings the dead reviewer already returned this round (best-effort from context — `$TMP-merged-r1.md` and the live scoped diff are authoritative, since round 1 isn't journaled yet). Fall back to `$ARGUMENTS`/the live scoped diff only if a file is somehow absent.
4. **If you still can't get a parseable `STATUS:` line, escalate to me** rather than proceeding or declaring the run converged.

**Round 1 reviewer context** (give this to the single reviewer; to *each* panelist in panel mode; and to the panel's post-merge reviewer per the panel section above):
- The original requirement **and the `$AC` checklist verbatim.**
- A summary of the implementation, and `$BASE` plus the exclusion list (`$TMP-exclude.txt` contents) so it pulls the diff scoped exactly as you do — `git diff $BASE -- . :(exclude)<path>…` **plus `git ls-files --others --exclude-standard -- . :(exclude)<path>…` (inspect each untracked file's contents)**, since the bare diff form is blind to new untracked files — the common TDD outcome (a new source module + test file, untracked at handoff) would otherwise be invisible to the reviewer. Verify the `$AC` criteria by hand instead.)** *(This bullet is for the **single reviewer**. In panel mode the panelists are read-only and skip it; the bite audit instead runs serially after the merge — see the panel section above.)*

It *may* flag missing frontend tests only where the code carries genuinely non-trivial logic (data transforms, multi-state branching, validation, reducers/state machines, logic-bearing hooks) that was left untested. Backend/business-logic coverage is still fair game as usual.

**Convergence is illegal** (the reviewer may not emit `STATUS: CONVERGED`) while *any* of these hold: an open blocker or should-fix, an unmet `$AC` criterion, or a test that failed the bite audit. `CONVERGED` means every blocker and should-fix is **resolved**, every `$AC` criterion is either met or marked "pending human visual check" (none left **unmet**), and all audited tests bite. **A criterion marked "pending human visual check" (a presentational item a headless agent can't confirm by eye) does NOT count as "unmet" for this purpose** — it is deferred to the Phase-3 human verification, not a convergence blocker; otherwise a clean all-presentational (zero-test) change could never legally converge and would burn all 3 rounds. (Confirm only that such criteria are *implemented and ready to be eyeballed*, not that they're "met.") A finding counts as **resolved** when it is *either fixed, or its rebuttal accepted by the reviewer* — a sustained rebuttal that the reviewer accepts is a valid resolution, not a blocker to convergence. (Open `nit`s do **not** block `CONVERGED`; only blockers and should-fixes do.) **When the reviewer emits `CONVERGED`, reconcile before accepting it:** confirm that every should-fix/blocker you *rebutted* (rather than fixed) was actually **conceded by the reviewer** in writing, not just dropped silently. If you find a finding you rebutted that the reviewer never affirmatively accepted, treat it as still open and `SendMessage` for an explicit concede-or-push-back before you exit. **In panel mode, also confirm the reviewer adjudicated every `recheck` nit** in its first response — for each `recheck` nit in `$TMP-merged-r1.md`, the reviewer must have either re-promoted it (now tracked as a blocker/should-fix) or explicitly stated it could not reproduce it. When findings come back, **you (the implementer) evaluate each finding on its merits** — do not reflexively agree:
- **Agree** → apply the fix (stay in TDD style: test first where it makes sense), and note "fixed: <finding>".
- **Disagree** → write a specific rebuttal explaining why the finding is wrong, out of scope, or already handled. For an evidence-backed finding, your rebuttal must address the repro directly (show why the repro is invalid or the behavior is actually correct).
- **Blockers are special:** you may not silently rebut a finding the reviewer rated `blocker`. Either fix it, or — if you genuinely believe it's wrong — escalate it for adjudication before exiting the loop (autonomous: emit `BLOCKED:{contested_blocker}` with both sides' reasoning). Do not self-resolve a contested blocker.

**Subsequent rounds (2 and 3):** `SendMessage` to the same reviewer with:
- Which findings you fixed (and how).
- Your rebuttals for the ones you disagreed with, with reasoning.
- A pointer to re-pull the updated diff (`git diff $BASE`) and re-run the tests.
Ask it to respond to your rebuttals (concede or push back with new reasoning), re-check any `$AC` criteria your fixes touched, re-run the bite audit on any tests your fixes changed, raise any new findings introduced by your fixes, and emit the `STATUS:` line again.

**Stopping conditions** (whichever comes first):
- The reviewer emits `STATUS: CONVERGED` → run the final green gate (below), then exit the loop.
- You complete **3 rounds** → stop regardless. Do not exceed 3 rounds. **Run the final green gate first** (it's required however the loop stops), then, if at this point any `blocker` is still open or contested, any **should-fix is still open or contested** (the reviewer sustains it and you haven't fixed it — it is not a "resolved" finding), any `$AC` criterion is still unmet, any test still fails the bite audit, **or (panel mode) any `recheck` nit the post-merge reviewer never adjudicated — re-promoted or explicitly dismissed — per the CONVERGED rule above**, escalate (autonomous: emit `BLOCKED:{round_cap_open_findings}`) rather than declaring the run done. (When you escalate, present each contested should-fix with both sides' reasoning labeled "contested — implementer-rebutted" so I can make a quick call.)

**Final green gate (required before you may exit the loop, however it stopped):** rounds 2–3 only re-run the tests and bite audit, so a late fix can introduce a type or lint error that nothing else catches. Before declaring the run done, re-run the **entire test suite, plus typecheck and lint if the project has them** — exactly the same gate as the Phase 1 handoff. Everything must be green. **Also verify the tree is implementation-only:** run `git status --porcelain` and the scoped `git diff $BASE -- . :(exclude)<path>…` (excluding any pre-existing paths recorded at the dirty-tree step — those are *expected* to remain and are **not** a dirty-tree failure) and confirm nothing remains from a reviewer's scratch/evidence test or an un-reverted bite break — the diff must contain only your implementation and tests, scoped to the requirement. If anything fails or the tree is dirty with non-implementation changes, fix/clean it (in TDD style where a test is warranted) and re-run until green; if you can't get it green within reason, escalate (autonomous: emit `BLOCKED:{final_gate_red}`) rather than exiting on a red gate.

After the loop, briefly summarize for me: the `$AC` checklist with final met/unmet status, what was fixed, what remains contested (with both sides' reasoning), and any findings deferred.
