You are the **implementer agent** and you own this entire run. The requirement to implement is:

$ARGUMENTS

Run the phases below in order. Do not skip phases. Narrate which phase and review round you're in as you go.

## Pre-flight (do this first, before parsing `$ARGUMENTS`)

1. **Confirm a git repo with commits.** Run `git rev-parse --is-inside-work-tree` and `git rev-parse HEAD`. If either fails (not a repo, or zero commits), stop and tell me — every later `git diff $BASE` depends on this.
2. **Choose the temp prefix `$TMP`** for every disposable file this run writes. Make it **deterministic and rediscoverable** rather than random, so a mid-run context summarization can't orphan the state files that hang off it: `$TMP=/tmp/tdd-review-loop-$(git rev-parse --show-toplevel | shasum | cut -c1-12)`. This is stable per checkout (so it survives context loss — **if you ever find yourself mid-run having lost `$TMP`, recompute it the same way before reaching for any state file**) and distinct across separate worktrees/checkouts (so genuinely concurrent runs in different trees never clobber each other's state; concurrent runs in the *same* tree already collide on shared test artifacts per the panel shared-tree caveat, so one prefix per tree is the right boundary). **Treat each `$TMP-<name>` file as freshly owned by this run** — overwrite `$TMP-base.sha`, `$TMP-ac.md`, `$TMP-exclude.txt`, `$TMP-panel-flag`, `$TMP-plan-path`, `$TMP-pre-snapshot.sha`, `$TMP-impl.sha`, `$TMP-panel-worktrees`, and `$TMP-merged-r1.md` at their write points, and start `$TMP-journal.md` empty, so leftovers from a prior crashed run in the same tree can't bleed in. **Several of these files are written only conditionally** (e.g. `$TMP-impl.sha` and `$TMP-panel-worktrees` only on the opt-in panel path, `$TMP-panel-flag`/`$TMP-plan-path` only when a flag/path was given), so a path that never writes one would otherwise *read a stale copy* from a prior crashed run — most dangerously a leftover `$TMP-impl.sha` spuriously gating the panel-teardown soft-reset. **So delete all of them up front now** (`rm -f` the whole `$TMP-*` set) before this run writes any, making "absent" reliably mean "not produced this run."

## Parse `$ARGUMENTS`

`$ARGUMENTS` is either an inline requirement/plan, or a path to a plan doc (e.g. `docs/some-plan.md`), optionally wrapped in a round-1 mode flag. Parse it in this exact order — the flag-and-conflict check runs **before** the empty-check:

1. **Detect the round-1 mode flag.** Look only at the **first and last whitespace-delimited tokens** of `$ARGUMENTS`. A token is a flag only if the *whole token* equals `--panel` or `--no-panel` — matched **case-sensitively as an ASCII literal** (two ASCII hyphens). `--PANEL`, a unicode-dash `—panel`, or a token like `--panel-feature.md` that merely *starts with* the string does **not** match (leave `$PANEL_FLAG` unset and fall through to the Phase-2 heuristic). Never infer the mode from the bare word "panel" inside the requirement text ("implement the admin **panel**" is a requirement, not a flag).
2. **Conflict check (first, before the empty-check).** Only when `$ARGUMENTS` has **at least two tokens** AND both the leading and trailing token are flags (a lone `--panel` is one token — it skips this check and goes straight to step 3):
   - **They disagree** (`--panel … --no-panel`): stop and ask me which mode I want — **even if no requirement text remains** after stripping them — and record **no** `$PANEL_FLAG` until I answer. When I answer, **persist it to `$TMP-panel-flag`** (step 3). Don't let the empty-check pre-empt this.
   - **They are identical** (`--panel … --panel`): they agree — record `$PANEL_FLAG` and persist it per step 3, **then** strip **both** tokens.
3. **Record and persist the flag.** If a (non-conflicting) flag is present — or once I resolve the conflict re-prompt in step 2 — record it as `$PANEL_FLAG` and **write it to `$TMP-panel-flag` immediately** — before any re-prompt below, and before the rest of git-hygiene — so a context summarization across the re-prompt or Phases 0–1 can't silently drop the mode I chose (you'll re-read it from there in Phase 2). Then strip the flag token(s) from `$ARGUMENTS`. If neither token is a flag, `$PANEL_FLAG` is unset and the mode is chosen by heuristic in Phase 2.
4. **Empty check.** If the remaining text is empty — originally empty, or empty after a flag strip (e.g. I passed only `--panel`) — ask me for the requirement before doing anything else. `$PANEL_FLAG` **persists across that re-prompt** (it's already on disk) and applies to the requirement I then supply — don't discard the mode I explicitly chose.
5. **Path vs. inline (decide on the *remaining* text).** It **"looks like a file path"** only if it is a single whitespace-free token that either contains a `/` separator or ends in a file extension (a `.<ext>` suffix). Anything else — multi-word text (even if it contains a slash, like "fix a/b testing bucket assignment"), or a bare single word with no extension (like "checkout") — is an **inline requirement**, not a path.
   - **Doc extension** (`.md`/`.txt`/`.rst`/`.markdown`): read the file and treat its contents as the requirement. **Persist the path to `$TMP-plan-path`** — Phase 3 needs it and it must survive summarization.
   - **Path-like but missing, unreadable, or empty:** stop and ask me, rather than silently treating the path string itself as the requirement.
   - **Path-like but NOT a doc extension** (a slash-bearing token, or any other extension — e.g. `src/auth/session.ts`, `infra/deploy.yaml`, `scripts/run.sh`, `config.json`): this could be source/config, not a plan. Don't silently distill acceptance criteria from it — **confirm with me** that I meant that file as the plan before proceeding. (Still persist the confirmed path to `$TMP-plan-path`.)

## Pre-run git hygiene (do this before capturing the base commit)

1. **Check for a dirty starting tree:** run `git status --porcelain`. If it's non-empty, the working tree already has changes that would otherwise be wrongly attributed to this requirement (folded into the diff the reviewer, the `$AC` pass, the bite audit, and the Phase-3 guide all consume). **Stop and ask me** how to proceed — stash, commit, or explicitly record the pre-existing paths so you can exclude them from "the diff" throughout. Do not silently absorb them. **If I choose to record paths**, extract a clean pathspec for each pre-existing entry into `$TMP-exclude.txt`, one per line — `git status --porcelain` lines are `XY <path>` (a 3-char status field then the path), so **strip the status field** (`cut -c4-`); for rename/copy entries (`R`/`C  old -> new`) record only the path **after `->`**; quote any path containing spaces (or capture with `git status --porcelain -z` and split on NUL). A raw porcelain line like ` M src/x.ts` fed straight to a pathspec will silently fail to exclude anything. That file becomes the canonical exclusion set used everywhere "the diff" is computed.
2. **Branch off the default/protected branch:** run `git branch --show-current`. If it's the default branch (`main`/`master`) or otherwise protected, `/tdd`'s red-green-refactor commits and bite-audit reverts would land directly on it. Create a feature branch (or ask me which) before Phase 1 so the run's commits are isolated.

**Then record the base commit so diffs work for the whole run regardless of what gets committed later:**
```
git rev-parse HEAD
```
Call this `$BASE`. **Persist it immediately** to `$TMP-base.sha` — `$BASE` is just a value in your context, and once `/tdd` starts committing you can no longer re-derive it from `git rev-parse HEAD`; re-read it from the file whenever you need it after commits land.

Throughout this run, "the diff" always means `git diff $BASE` plus `git status --porcelain` for any untracked files (and `git diff $BASE -- <new files>` once added), **minus any pre-existing paths recorded in step 1**. Never rely on a bare `git diff`, which shows only unstaged changes and will miss work that TDD has already committed or staged.

**Propagating the exclusion set:** if step 1 recorded pre-existing paths to `$TMP-exclude.txt`, that file is the canonical exclusion set. Anywhere this run computes "the diff" — including the Phase-2 mode heuristic, every reviewer/panelist, and the Phase-3 guide agent — scope it explicitly, e.g. `git diff $BASE -- . $(sed 's/^/:(exclude)/' $TMP-exclude.txt)` (this `$(...)` form assumes space-free paths; for paths with spaces, pass the `:(exclude)<path>` pathspecs as explicit quoted arguments instead), and paste both `$BASE` (from `$TMP-base.sha`) and the contents of `$TMP-exclude.txt` into each subagent's prompt so they see the same scoped diff you do. If no paths were recorded, the exclusion set is empty and a bare `git diff $BASE` is already correct.

## Phase 0 — Acceptance criteria

Before writing any code, distill the requirement into an explicit, **numbered acceptance-criteria checklist** — each item a single observable behavior or constraint the finished work must satisfy, phrased so it can be objectively checked as met/unmet (not "handles errors well" but "returns a 422 with field-level messages when the payload is missing `email`"). Include negative/edge criteria where the requirement implies them. For a purely presentational criterion that can only be confirmed by eye (spacing, font, layout), mark it as such — it will be verified by human visual check, not asserted "met" by a headless agent.

Show me the checklist and **get my confirmation before implementing.** If I give edits, apply them and **restate the final checklist, then loop** — confirm again — until I approve it with no further edits (don't proceed on your own interpretation of an edit). If the requirement is a one-line bug fix, this can be a single criterion — but still write it down (you may fold this single-criterion confirmation into the same message as your implementation plan). This checklist (call it `$AC`) is the contract for the whole run: it scopes Phase 1, it's what the reviewer ticks off in Phase 2, and convergence is illegal while any criterion is unmet (see Phase 2).

**Persist `$AC` so it survives verbatim across subagent handoffs:** once I approve it, write the final checklist to `$TMP-ac.md` (the same disposable-file pattern this command uses for `$BASE`, the exclusion list, and the Phase-3 guide). Treat that file as the source of truth and **re-read it** at each handoff (every reviewer spawn, every `SendMessage`, the Phase-3 spawn) rather than relying on it staying intact in your context — paste its exact contents into each subagent prompt.

## Phase 1 — Implement with TDD

Invoke the `/tdd` skill and implement the requirement using its red-green-refactor workflow. Follow `/tdd` fully, including confirming the interface and which behaviors to test with me where that skill calls for it. Every `$AC` criterion that warrants a test (per the scoping rules below) should map to at least one test.

**Frontend test scoping:** Do *not* write tests for frontend/UI code by default. Skip tests for presentational components, layout/styling, simple prop wiring, trivial event handlers, and thin glue that just calls a hook or renders data. Only write frontend tests when the code carries **non-trivial logic worth protecting** — e.g. meaningful data transformation/derivation, conditional branching with several states, form validation rules, reducers/state machines, custom hooks with real logic, or tricky edge-case handling. In that case, prefer testing the logic in isolation (extract it to a pure function/hook and test that) rather than rendering the whole component. When in doubt about whether a given piece of frontend logic is "complex enough," ask me before writing or skipping the test. This scoping rule applies only to frontend code; backend/business logic follows `/tdd` as normal.

**Note:** this phase is *not* fully autonomous — `/tdd` will pause to get my approval on the interface and the list of behaviors to test. That's expected; wait for my input at those checkpoints rather than guessing.

When implementation is complete, **gate the handoff on a fully green state**: run the entire test suite, plus typecheck and lint if the project has them. Everything must pass before moving to Phase 2 — don't make the reviewer burn a round on breakage you could catch here. **If `/tdd` can't reach green within reason** (the implementation keeps failing and you're stuck), escalate to me rather than handing off red or thrashing — the same stop-and-ask discipline the Phase 2 gates apply.

**Bite check (do this yourself before handoff):** for each of your 2–3 most important new tests, deliberately break the code it covers (flip a condition, drop a guard, return the wrong value) and confirm that test *fails*, then revert. A test that stays green against broken code is not protecting anything — fix or strengthen it before handoff. (If only one test exists, bite-check that one.) Record which tests you bite-checked; you'll report this to the reviewer.

**Make every bite revert-safe** (here and everywhere else this run breaks-then-reverts code — the reviewer's bite audit too): snapshot before breaking and restore from the snapshot rather than hand-editing the break back, so a crash mid-break can't leave the tree broken. Concretely: stash or commit clean state first (e.g. `git stash` / a throwaway WIP commit, or note the exact `git checkout -- <file>` that restores it), break, observe the failure, then **restore from the snapshot** and verify `git diff $BASE` is back to where it was. If you ever find the tree broken with no record of how to restore it, stop and tell me rather than guessing.

**Zero-test branch:** if the requirement legitimately warrants no tests (e.g. a purely presentational frontend change under the scoping rule above), the test-centric gates degrade gracefully — make that explicit rather than inventing tests to satisfy them: the bite check and the reviewer's bite audit are **N/A**, "all audited tests bite" is **vacuously true**, and both green gates fall back to **typecheck + lint + manual `$AC` verification** (walk each criterion by hand, since there are no tests to assert it — and for any presentational criterion that can only be confirmed by eye, mark it "pending human visual check," not "verified met"). Say so in your handoff summary so the reviewer doesn't raise "missing tests" against an intentionally test-free change.

Then capture a summary of what you built (files changed, key decisions, the diff — computed per the "the diff" definition in the Pre-run git-hygiene section: `git diff $BASE` **plus** any untracked files, scoped by the exclusion list — the `$AC` checklist with each item mapped to where it's satisfied + tested, and your bite-check results) — you'll hand this to the reviewer.

## Phase 2 — Review loop (up to 3 rounds)

### Round-1 mode: single reviewer vs. reviewer panel

Round 1 is the discovery round — breadth matters most here. You may run it either as a single reviewer or as a parallel **panel** of lens-specialized reviewers whose findings you merge. Rounds 2–3 are *always* a single-reviewer dialogue regardless of round-1 mode (see below).

Decide the mode before spawning anything, in this order:
1. **If `$PANEL_FLAG` is set:** re-read it from `$TMP-panel-flag` (don't trust it surviving in context across Phases 0–1) — `--panel` → use the panel; `--no-panel` → use a single reviewer. The flag always wins. If `$TMP-panel-flag` is absent or empty, treat the flag as **unset** and fall through to the heuristic below rather than guessing a mode.
2. **Otherwise, heuristic on the Phase 1 diff:** use the **panel** if the diff touches **≥3 files** OR has **≥150 changed lines** (measure with `git diff $BASE --shortstat` **scoped to exclude any recorded pre-existing paths** in `$TMP-exclude.txt`, so a dirty starting tree can't inflate the count: insertions + deletions) OR touches core business logic / a known high-risk area **and** the diff is non-trivial (don't spin up a 4-reviewer panel for a 2-line fix on the high-risk disjunct alone); otherwise use a **single reviewer**.

**Announce-and-proceed:** state in one line which mode you're using and why (e.g. "Round-1 mode: panel — diff touches 6 files / 240 lines" or "Round-1 mode: single — 1 file, 18 lines"), then proceed. Don't stop to ask; I'll override if I disagree.

**Panel mode — round 1 only.** Spawn 3–4 `general-purpose` reviewers in parallel (single message, multiple tool calls). **Default to all 4 lenses** (below); drop to 3 only for a smaller-but-still-panel-worthy diff (see the fold-down note). Give each the same round-1 reviewer context (requirement, `$AC`, `$BASE` and the exclusion list, implementation summary, frontend scoping rule), with two differences: assign each a distinct **lens** and tell it to confine its findings to that lens, and tell it it is **read-only** — it may read and report, but must not edit/mutate the tree.

**Read-only evidence gate for panelists (replaces the write-and-run evidence gate):** because panelists are read-only and (mostly) don't run the suite, do **not** hold them to the Phase-2 evidence gate that demands a failing test they wrote and ran. Instead require each panel finding to cite a specific `file:line` and give precise **observed-vs-expected reasoning** (what the code does on what input vs. what it should do). Panel findings are **provisional**: the single post-merge reviewer (below) converts the surviving ones into evidence-backed findings before convergence is judged — so a real bug a panelist spots is never demoted to `nit` merely for lacking a written repro.

**Shared-tree caveat (important — the panel shares one working tree):** there is no harness-level write lock, so "read-only" is an *instruction the panelist may still violate*, and **concurrent test runs collide** on non-namespaced artifacts (`.pytest_cache`, coverage files, `__pycache__`, snapshots, `dist`/`build`/`target`, test DBs, fixed ports), producing flaky failures a panelist would then misreport as a real finding. So do **not** have all panelists run the suite. Choose one:

- **Default — single source of truth (static panel):** have exactly **one** panelist (or none) run the suite; the others review statically and against the green suite output you already captured at the Phase 1 handoff. Tell the static panelists explicitly: do not run the suite. Their findings follow the read-only evidence gate above (`file:line` + observed-vs-expected reasoning), so not running the suite does **not** cap them at `nit`. **This is the default** — it has no worktree/commit state to strand, and the read-only gate plus the serial post-merge re-verification already give full-severity coverage without concurrent suite runs.
- **Opt-in — per-panelist checkout (only if you genuinely need panelists to run the suite concurrently):** give each panelist its own worktree so their suite runs don't collide. This path carries extra git state, so follow the numbered setup and **always** run "Panel teardown" (below) on every exit:
  1. **Record `$PRE_SNAPSHOT`** = `git rev-parse HEAD` — **unconditionally**, even if the tree is clean — and persist it to `$TMP-pre-snapshot.sha`.
  2. **If the tree has uncommitted work,** capture *everything, including untracked new files*, in a WIP commit the worktrees can point at: `git add -A && git commit -m wip-panel-snapshot`. Use `git add -A`, **not** `git commit -am` (which stages only modified *tracked* files and silently drops untracked new files). Call this commit `$IMPL` and persist `$IMPL` = `git rev-parse HEAD` to `$TMP-impl.sha`. **If the tree is already clean** (the common case after `/tdd` commits its work), make no commit — `$IMPL` is simply HEAD; you'll skip the soft-reset in teardown step 2 (no WIP commit to unwind) but still run the HEAD-equality assert in step 3, where it's a trivially-passing no-op.
  3. **`git worktree add` each throwaway worktree at `$IMPL`, not `$BASE`** — a worktree at `$BASE` predates Phase 1 and contains none of the implementation, so `git diff $BASE` inside it would be empty and every panelist would review the wrong tree. **Record each worktree path to `$TMP-panel-worktrees`** (one per line) so teardown can find them after a context drop.
  4. **Sanity-check that one worktree reproduces the implementer's full "diff"** — per the "the diff" definition in the Pre-run git-hygiene section, `git diff $BASE` **plus** the `git status --porcelain` untracked set, scoped by the exclusion list, not a bare `git diff $BASE` (which is blind to a dropped untracked file on both sides). **If that sanity check fails,** do **not** run the panel on a wrong tree — run **Panel teardown** now, then fall back to the static option above, or stop and ask me.
  5. With a verified worktree, the panelists may each run the suite safely.

  **Panel teardown — run on EVERY exit from the opt-in worktree path,** and on every exit path: panelists returned normally, one errored/aborted, the sanity check failed, you fell back to static, or you stopped to ask me. Re-read state from the `$TMP-*` files (a context drop may have lost the in-memory values):
  1. Remove **every** worktree listed in `$TMP-panel-worktrees`: `git worktree remove --force <path>` each, then `git worktree prune`. (If a worktree won't remove, stop and tell me rather than leaving it to collide with the next run.)
  2. **Detect and revert any panelist mutation — always, on both the clean and dirty paths:** run `git diff $IMPL` (on the clean path `$IMPL` is HEAD, so this is well-defined either way) — it's empty unless a panelist edited the tree despite the read-only instruction. Revert only those specific stray paths with `git checkout -- <paths>`. **Then, only if you made the `$IMPL` WIP commit** (`$TMP-impl.sha` exists for this run), `git reset --soft $PRE_SNAPSHOT` (re-read from `$TMP-pre-snapshot.sha`) to un-commit the implementation back to the Phase 1 state.
  3. **Assert HEAD == `$PRE_SNAPSHOT`.** The porcelain/diff checks below cannot see a stranded `wip-panel-snapshot` commit — the tree content is identical whether or not it's dropped — so this HEAD-equality check is the **only** guard against leaving a stray commit on the feature branch. (On the clean path no commit was made, so the assert passes trivially — run it anyway.)
  4. Run `git status --porcelain` and the scoped `git diff $BASE` to confirm the tree matches the Phase 1 handoff. **If you soft-reset a dirty handoff, a non-empty porcelain is *expected*** — that's the uncommitted Phase 1 implementation, not a failure. Do **not** blanket `git checkout -- .`; stray panelist paths were already reverted in step 2.

  On the static (default) path no worktrees or WIP commit exist, so teardown reduces to confirming via `git status --porcelain`/`git diff $BASE` that the tree still matches the Phase 1 handoff — and `git checkout`/`git stash` away any stray change a panelist made despite the read-only instruction.

Either way, tell every panelist it must **not** emit a `STATUS:` line (convergence is judged only by the single reviewer in the dialogue rounds). The lenses:
- **correctness** — logic bugs, wrong outputs, broken control flow, mishandled return values.
- **edge-cases / concurrency** — boundaries, nulls/empties, error paths, races, ordering, partial failures.
- **requirements-coverage** — walk the `$AC` checklist; find criteria that are unmet, partially met, or untested.
- **test-quality** — by inspection only: find weak, tautological, or non-biting tests and untested logic, and **nominate** the 2–3 tests most worth a bite audit (don't run the audit — that's deferred to the serial step below). *(If Phase 1 was the intentional **zero-test** case, this lens instead confirms no tests were warranted — there's nothing to nominate, and that's expected, not a finding — but it should still flag any genuinely non-trivial logic that was left untested, per the Phase-1 frontend scoping rule.)*

(For a smaller-but-still-panel-worthy diff, drop to 3 lenses by folding edge-cases into correctness.)

When the panelists return — **even if one errored or aborted** — **first run Panel teardown** (above) to restore a clean tree on every exit path, and confirm the tree still matches the Phase 1 handoff state. Then **merge their findings** into one numbered list:
- Collapse entries only when they describe the **same defect / root cause** (not merely the same `file:line`), keeping the highest severity and strongest evidence.
- Demote any blocker/should-fix that failed the **read-only evidence gate** (no `file:line`, *or* no observed-vs-expected reasoning) to an unverified `nit` — but **tag it `recheck`**. A `recheck` nit is not a silently-ignored finding: the post-merge reviewer (below) must independently re-investigate every `recheck` nit before its first `STATUS:` and **re-promote** any it can reproduce, so a real bug a panelist spotted but under-documented can't slip out as a non-blocking nit.
- Carry the test-quality lens's bite-audit nominations forward separately.
- **Persist the merged list to `$TMP-merged-r1.md`** — it's the round-1 reconstruction source if the post-merge reviewer dies (see below). **Produce it even if it's empty.**

(Panelists are discarded after round 1 — don't try to resume them.)

Then spawn **one** `general-purpose` reviewer — **always spawn it, even if the merged list is empty**, since it is the only source of the round-1 `STATUS:` line. **Hand it the full single-reviewer "Round 1 reviewer context" block below** (requirement, `$AC` verbatim, `$BASE` and the exclusion list, the evidence gate, the acceptance-criteria pass, frontend scoping, etc.) *plus* the merged list as the round-1 findings — it owns the `$AC` pass and the convergence judgement from here on, so it must not be left to re-derive that context. It now has the tree to itself, so it must also re-establish evidence: convert the panel's **provisional** findings into evidence-backed ones under the real evidence gate, **independently re-investigate every `recheck` nit and re-promote any it reproduces**, and run the **test-bite audit serially** on the nominated tests (plus any others it judges important): break the covered code, confirm the test fails, revert. Any test that stays green against broken behavior becomes a `blocker` ("test does not bite") added to the findings. **(If Phase 1 was the intentional zero-test case, the bite audit is N/A — see the Phase-1 zero-test branch; say so and verify `$AC` by hand instead of inventing tests.)** **Instruct it to emit the `STATUS:` line in this first response** (covering the merged list plus its bite-audit result) — otherwise panel mode has no round-1 convergence signal and a clean diff can't exit early. Then proceed with rounds 2–3 as the single-reviewer dialogue below.

**Single-reviewer mode (and rounds 2–3 of both modes):**
Spawn a **single** reviewer subagent with the `general-purpose` agent type and keep using that same agent across all rounds via `SendMessage` (so its context and prior findings are preserved — this is a real dialogue, not three fresh reviews). **Record the reviewer's agent id/name the moment you spawn it** — note it in your working state **and append it to `$TMP-journal.md`** — so `SendMessage` resume is the reliable path in rounds 2–3 and you don't lose the handle. **After each round, journal that round to `$TMP-journal.md`:** the reviewer's findings, your fix/rebuttal for each, and the `STATUS:` line — this is the durable transcript the fallback below reconstructs from.

**Fallback if the reviewer can't be resumed:** if `SendMessage` to the prior reviewer isn't available or the agent wasn't retained between rounds, re-spawn a fresh `general-purpose` reviewer and paste the full prior-round transcript (re-read it from `$TMP-journal.md`) into its prompt — every prior finding, your fix/rebuttal for each, and the current status — so its context is reconstructed. Never let the loop silently degrade into three context-free reviews.

**Missing or unparseable round-1 `STATUS:` line:** the stopping conditions are evaluated by reading the reviewer's `STATUS:` line, so a *round-1* reviewer (the single-mode reviewer, or the panel's post-merge reviewer) that crashes, aborts, or returns no parseable `STATUS:` leaves the loop with no convergence signal — and round 1 has not yet been journaled, so `$TMP-journal.md` holds no round transcript yet (only the spawn-time agent id). **Never treat an absent `STATUS:` as `CONVERGED`.** Instead: if the reviewer is still live, `SendMessage` it once asking only for the `STATUS:` line; if it died or still returns nothing parseable, re-spawn a fresh `general-purpose` reviewer and reconstruct its context from `$TMP-ac.md`, `$BASE`/the exclusion list, the panel's merged findings (`$TMP-merged-r1.md`, in panel mode), and any findings the dead reviewer already returned in this round (the requirement text and implementation summary aren't separately persisted — reconstruct them from `$ARGUMENTS`/`$TMP-plan-path` and the live scoped diff) — not the round-by-round journal, which is still empty this early. If you still can't get a parseable `STATUS:` line after that, escalate to me rather than proceeding or declaring the run converged.

**Round 1 reviewer context** (give this to the single reviewer; to *each* panelist in panel mode; and to the panel's post-merge reviewer per the panel section above):
- The original requirement **and the `$AC` checklist verbatim.**
- A summary of the implementation, and `$BASE` plus the exclusion list (`$TMP-exclude.txt` contents) so it pulls the diff scoped exactly as you do — `git diff $BASE -- . :(exclude)<path>…`. Instruct it to **actually explore the surrounding code and run the test suite itself** — it has the tools — rather than reviewing the pasted diff in isolation, so it can verify claims and catch integration issues.
- Instruct it to act as an adversarial code reviewer: find correctness bugs, missed requirements, missing/weak test coverage, edge cases, and design problems. Return a numbered list of findings, each with severity (blocker / should-fix / nit) and a concrete rationale.
- **Evidence gate (required for every blocker and should-fix):** each such finding must cite a specific `file:line`, **and** carry proof it's real — *either* a failing test the reviewer actually wrote and ran (paste the test and the failure output) *or* exact reproduction steps (commands + observed vs. expected output). A finding at blocker/should-fix severity **without** a repro must be demoted to `nit` and labeled "unverified — could not reproduce." This applies the same skeptic's burden to the reviewer that it applies to you: no plausible-but-unproven blockers.
- **Leave the tree as you found it:** a written evidence test is by definition *failing* and would either ride into the deliverable diff or turn the implementer's final green gate red on a test it never authored. So the reviewer must paste its evidence/scratch tests into the report rather than leaving them in the tree: after gathering evidence and running the bite audit, **delete every scratch/evidence test and revert every bite break**, then confirm the diff — scoped per the exclusion list, `git diff $BASE -- . :(exclude)<path>…` — is back to implementation-only before responding (any pre-existing paths from the dirty-tree step are expected to remain and don't count). The tree handed back must contain only the implementer's work.
- **Acceptance-criteria pass:** walk the `$AC` checklist and mark each criterion met / unmet / untested-but-met / pending human visual check (the last for presentational criteria a headless agent can't confirm by eye — don't mark those "met"), citing where in the code/tests each is satisfied. Any unmet criterion is at least a `should-fix` (a blocker if it's core to the requirement). *(In panel mode this is the **requirements-coverage** lens's job; other panelists skip it.)*
- **Test-bite audit:** independently pick 2–3 of the most important tests, deliberately break the covered code, and confirm the test fails (then revert). Any test that stays green against broken behavior is a `blocker` ("test does not bite"). I already did a self bite-check on [the tests you bit] — spot-check *different* tests where possible (if only one test exists, re-bite it yourself). **(If Phase 1 was the intentional zero-test case, this audit is N/A — there are no tests to bite; that's vacuously satisfied per the Phase-1 zero-test branch, not a finding. Verify the `$AC` criteria by hand instead.)** *(This bullet is for the **single reviewer**. In panel mode the panelists are read-only and skip it; the bite audit instead runs serially after the merge — see the panel section above.)*
- Tell it about the **frontend test scoping rule** from Phase 1: trivial/presentational frontend code is intentionally left untested, so it should **not** raise "missing test coverage" findings for it. It *may* flag missing frontend tests only where the code carries genuinely non-trivial logic (data transforms, multi-state branching, validation, reducers/state machines, logic-bearing hooks) that was left untested. Backend/business-logic coverage is still fair game as usual.
- Instruct it to **end every response with an explicit status line** so the loop is machine-checkable: either `STATUS: CONVERGED` or `STATUS: OPEN — blockers:N should-fix:M nits:K ac-unmet:U bite-failures:B`. *(Panel-mode exception: the read-only **panelists** must NOT emit a `STATUS:` line — only the single reviewer / the panel's post-merge reviewer does. When you hand this block to panelists, drop this bullet.)*

**Convergence is illegal** (the reviewer may not emit `STATUS: CONVERGED`) while *any* of these hold: an open blocker or should-fix, an unmet `$AC` criterion, or a test that failed the bite audit. `CONVERGED` means every blocker and should-fix is **resolved**, every `$AC` criterion is met, and all audited tests bite. A finding counts as **resolved** when it is *either fixed, or its rebuttal accepted by the reviewer* — a sustained rebuttal that the reviewer accepts is a valid resolution, not a blocker to convergence. (Open `nit`s do **not** block `CONVERGED`; only blockers and should-fixes do.) **When the reviewer emits `CONVERGED`, reconcile before accepting it:** confirm that every should-fix/blocker you *rebutted* (rather than fixed) was actually **conceded by the reviewer** in writing, not just dropped silently. If you find a finding you rebutted that the reviewer never affirmatively accepted, treat it as still open and `SendMessage` for an explicit concede-or-push-back before you exit.

When findings come back, **you (the implementer) evaluate each finding on its merits** — do not reflexively agree:
- **Agree** → apply the fix (stay in TDD style: test first where it makes sense), and note "fixed: <finding>".
- **Disagree** → write a specific rebuttal explaining why the finding is wrong, out of scope, or already handled. For an evidence-backed finding, your rebuttal must address the repro directly (show why the repro is invalid or the behavior is actually correct).
- **Blockers are special:** you may not silently rebut a finding the reviewer rated `blocker`. Either fix it, or — if you genuinely believe it's wrong — escalate it to me for adjudication before exiting the loop. Do not self-resolve a contested blocker.

**Subsequent rounds (2 and 3):** `SendMessage` to the same reviewer with:
- Which findings you fixed (and how).
- Your rebuttals for the ones you disagreed with, with reasoning.
- A pointer to re-pull the updated diff (`git diff $BASE`) and re-run the tests.
Ask it to respond to your rebuttals (concede or push back with new reasoning), re-check any `$AC` criteria your fixes touched, re-run the bite audit on any tests your fixes changed, raise any new findings introduced by your fixes, and emit the `STATUS:` line again.

**Stopping conditions** (whichever comes first):
- The reviewer emits `STATUS: CONVERGED` → run the final green gate (below), then exit the loop.
- You complete **3 rounds** → stop regardless. Do not exceed 3 rounds. **Run the final green gate first** (it's required however the loop stops), then, if at this point any `blocker` is still open or contested, any **should-fix is still open or contested** (the reviewer sustains it and you haven't fixed it — it is not a "resolved" finding), any `$AC` criterion is still unmet, or any test still fails the bite audit, escalate to me rather than declaring the run done. (When you escalate, present each contested should-fix with both sides' reasoning labeled "contested — implementer-rebutted" so I can make a quick call.)

**Final green gate (required before you may exit the loop, however it stopped):** rounds 2–3 only re-run the tests and bite audit, so a late fix can introduce a type or lint error that nothing else catches. Before declaring the run done, re-run the **entire test suite, plus typecheck and lint if the project has them** — exactly the same gate as the Phase 1 handoff. Everything must be green. **Also verify the tree is implementation-only:** run `git status --porcelain` and the scoped `git diff $BASE -- . :(exclude)<path>…` (excluding any pre-existing paths recorded at the dirty-tree step — those are *expected* to remain and are **not** a dirty-tree failure) and confirm nothing remains from a reviewer's scratch/evidence test or an un-reverted bite break — the diff must contain only your implementation and tests, scoped to the requirement. If anything fails or the tree is dirty with non-implementation changes, fix/clean it (in TDD style where a test is warranted) and re-run until green; if you can't get it green within reason, escalate to me rather than exiting on a red gate.

After the loop, briefly summarize for me: the `$AC` checklist with final met/unmet status, what was fixed, what remains contested (with both sides' reasoning), and any findings deferred.
